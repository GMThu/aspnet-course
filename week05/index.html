POINT 01 · GET VS POST

GET 是拿報名頁，
POST 是交出欄位資料。

第一次開啟首頁，瀏覽器向伺服器拿 HTML；填完按下送出，才把 form 內的資料交給後端。

GET／拿頁面

瀏覽器 ── GET / ──→ 伺服器 瀏覽器 ←── 表單 HTML ──

對應 Razor Pages 的 OnGet。

POST／交資料

瀏覽器 ── POST / ─→ 伺服器 名稱、Email、場次

對應今天要完成的 OnPost。

先記「拿」和「交」，不背 HTTP 大全05

POINT 02 · FORM BOUNDARY

form 像一個資料信封，
只有信封裡的欄位會一起送出。

<form method="post"> <label>顯示名稱</label> <input ...> <button type="submit"> 送出報名 </button> </form>

先預測

如果 input 放在 </form> 後面，按下送出時，它會一起送嗎？

先選答案，再用「信封範圍」解釋。

method="post" 描述這次送出的方式06

POINT 03 · LABEL BEFORE STYLE

label 不是裝飾，
它把「問題」和「輸入位置」連起來。

點一下「顯示名稱」，游標也會進入輸入框。

<label for="nameDemo"> 顯示名稱 </label> <input id="nameDemo">
Placeholder 只是範例，輸入後會消失；不能取代 label。
可操作與可理解，先於漂亮07

POINT 04 · TAG HELPER

asp-for 告訴 Razor：
這個欄位對應哪一個 C# 屬性。

Pages/ ├─ Index.cshtml └─ Index.cshtml.cs
<label asp-for="Input.DisplayName"></label> <input asp-for="Input.DisplayName" class="form-control">
畫面欄位Input.DisplayName
↔
C# 屬性Input.DisplayName

兩邊名稱一致，才能沿著同一條資料線走。

先看懂對應關係，不背生成後的 HTML08

POINT 05 · PAGE MODEL

Index.cshtml 負責呈現，
Index.cshtml.cs 負責處理。

同一個 Razor Page 有兩個合作檔案：一個面對使用者，一個接住請求與資料。

Pages/ ├─ Index.cshtml │ └─ 表單、欄位、錯誤、結果 │ └─ Index.cshtml.cs └─ 屬性、OnGet、OnPost、驗證
前端與後端分工，但共同完成一頁11

POINT 06 · INPUT MODEL

四個欄位，不要散成四條線；
用一個 Input 物件收在一起。

public class RegistrationInput { public string DisplayName { get; set; } public string Email { get; set; } public string Session { get; set; } public string Note { get; set; } }
InputDisplayName
InputEmail
InputSession
InputNote
同一個用途的輸入，組成一個模型12

POINT 07 · MODEL BINDING

[BindProperty] 讓 ASP.NET
把 POST 欄位放進 Input。

[BindProperty] public RegistrationInput Input { get; set; } = new RegistrationInput();

Binding 做了什麼？

  1. 找出送來的欄位名稱。
  2. 比對 Input.DisplayName 等屬性。
  3. 把文字轉成屬性需要的型別。
  4. 記錄轉換與驗證錯誤。
它不是資料庫。Binding 只把這次請求帶來的值放進 C# 物件。
收到資料 ≠ 保存資料13

POINT 08 · HANDLER

表單用 POST 送出時，
Razor Pages 會尋找 OnPost()。

public bool Submitted { get; set; } public void OnPost() { Submitted = true; }

和 OnGet 的分工

OnGet：第一次開啟頁面。

OnPost：使用者送出表單。

現在還沒有檢查內容。空白資料也會被當成成功；第三節才加上驗證閘門。
先讓流程走通，再增加規則14

POINT 09 · RESPONSE

成功摘要不是另一個神祕頁面，
是 Razor 根據狀態決定要不要顯示。

@if (Model.Submitted) { <section class="alert alert-success"> 報名資料已收到 參加者：@Model.Input.DisplayName </section> }

現在能證明什麼？

後端收到這次 POST，並把 Input 的值放回 HTML 回應。

還不能證明什麼？

不能證明資料已存入 SQL Server，也不能證明重新啟動後還找得到。

正確描述系統現在做到哪裡16

POINT 10 · RECEIVED ≠ VALID

後端收到資料，
不代表資料合理。

空白名字、錯誤 Email、未選場次都能被傳送。驗證的工作，是在成功之前設一道明確閘門。

報名資料已收到？

參加者：（空白）

Email：abc

場次：請選擇

這些資料雖然送到了，但不應通過。
接收是技術事實，接受是規則判斷19

POINT 11 · RULES BESIDE DATA

每個驗證標記，只回答一個問題。

[Required(ErrorMessage = "請輸入顯示名稱")] [StringLength(20, ErrorMessage = "最多 20 字")] [Display(Name = "顯示名稱")] public string DisplayName { get; set; }

Required

可以空白嗎？

StringLength

最多可以多長？

Display

畫面上要叫什麼名字？

一條規則，一個可測試問題20

POINT 12 · VALIDATION GATE

先問 ModelState.IsValid，
通過才打開成功區。

public void OnPost() { if (!ModelState.IsValid) { return; } Submitted = true; }
規則未通過留在表單，顯示錯誤
全部通過顯示成功摘要

如果先設定 Submitted，再檢查 ModelState，空白資料也可能出現成功訊息。

成功訊息必須在驗證之後21

POINT 13 · SHOW THE REPAIR PATH

驗證不是只說「失敗」，
要讓使用者知道哪裡需要修。

<label asp-for="Input.Email"></label> <input asp-for="Input.Email" class="form-control"> <span asp-validation-for="Input.Email" class="text-danger"></span>

Email 格式不正確

錯誤靠近欄位；修正後可以再次送出。

錯誤訊息本身也是介面設計22

POINT 14 · TEST BEHAVIOR

只測成功一次，不能證明驗證有效。

測試路線輸入應該看到操作
空白所有必填欄空白必填錯誤；沒有成功摘要
錯誤格式Email = abcEmail 格式錯誤
正確課堂假資料成功摘要與輸入一致
選一條路，觀察預期行為。之後要在自己的 localhost 重做。
失敗路線也要有明確預期23

PAIR TEST

測試者不改程式，
只交付一份可重現的回報。

1

輸入

清楚說明用了哪一組假資料。

2

操作

說明按了什麼、在哪個畫面發生。

3

結果

比較預期與實際，不只說「壞掉」。

回報句型：「我輸入＿＿，按下送出後，預期＿＿，實際看到＿＿；請先檢查＿＿。」
使用課堂假資料；不要輸入真實 Email、電話、密碼、連線字串或 API key。
好回報能讓下一個修改更小、更準26
