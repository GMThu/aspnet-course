MODEL 01 · DATA SHAPE

Model 先不用想得很抽象：
它描述這筆資料有哪些欄位。

不是畫面

HTML 決定使用者看到與操作什麼。

不是資料庫

物件現在只存在記憶體，重新啟動不會留下。

是一個結構

屬性名稱與型別，說明這筆輸入長什麼樣子。

本週的 Model 指 RegistrationInput；PageModel 指整個 Razor Page 的後端處理類別。
先分清 Input Model、PageModel 與資料庫04

MODEL 02 · ONE PROPERTY

一個屬性，就是物件裡一個有名字的位置。

先只看顯示名稱，不一次吞下整個 class。

public class RegistrationInput

}}

→

MODEL 03 · TYPE

型別先回答：這個位置可以放什麼？

string

文字：名稱、Email、場次、備註。

int

整數：未來若加入報名人數，可用數值規則。

bool

是／否：例如是否同意條款；不適合拿來存名稱。

型別不是驗證全部。string 能裝下 abc，但那不代表它是合法 Email。
型別管資料種類；驗證管業務規則06

MODEL 04 · INPUT MODEL

四個欄位，不要散成四條線；
用一個 Input 物件收在一起。

public class RegistrationInput { public string DisplayName { get; set; } = string.Empty; public string Email { get; set; } = string.Empty; public string Session { get; set; } = string.Empty; public string? Note { get; set; } }
必填文字string＋空字串起點
選填文字string? 可沒有值
物件四個屬性收成一組
? 表示允許沒有值；它不會自動限制長度或 Email 格式。
型別與 nullable 先說清楚，再加入驗證規則07

MODEL 05 · MAPPING

asp-for 寫的路徑，
就是 Binding 要找的目的地。

Razor 欄位

<input asp-for="Input.DisplayName">

C# 目的地

public RegistrationInput Input {{ get; set; }}
public string DisplayName {{ get; set; }}
Input.DisplayName 先找 Input，再找裡面的 DisplayName；任何一段拼錯都會斷線。
讓學生用手指出路徑的兩段08

VALIDATION 01 · RECEIVED ≠ VALID

後端收到資料，
不代表資料合理。

空白名字、錯誤 Email、未選場次都能被傳送。驗證的工作，是在成功之前設一道明確閘門。

報名資料已收到？

參加者：（空白）

Email：abc

場次：請選擇

這些資料雖然送到了，但不應通過。
接收是技術事實，接受是規則判斷11

VALIDATION 02 · RULES BESIDE DATA

每個驗證標記，只回答一個問題。

[Required(ErrorMessage = "請輸入顯示名稱")] [StringLength(20, ErrorMessage = "最多 20 字")] [Display(Name = "顯示名稱")] public string DisplayName { get; set; }

Required

可以空白嗎？

StringLength

最多可以多長？

Display

畫面上要叫什麼名字？

一條規則，一個可測試問題12

VALIDATION 03 · ONE RULE

不要背整串；
逐條問它在防什麼。

[Required]

有沒有填？空白不能通過。

[EmailAddress]

有填時，格式像不像 Email？

[StringLength(20)]

文字長度是否超過上限？

[Display] 改善顯示名稱，本身不是「擋資料」的驗證規則。
一條規則配一條可重現測試13

VALIDATION 04 · VALIDATION GATE

先問 ModelState.IsValid，
通過才打開成功區。

public void OnPost() { if (!ModelState.IsValid) { return; } Submitted = true; }
規則未通過留在表單，顯示錯誤
全部通過顯示成功摘要

如果先設定 Submitted，再檢查 ModelState，空白資料也可能出現成功訊息。

成功訊息必須在驗證之後14

VALIDATION 05 · SHOW THE REPAIR PATH

驗證不是只說「失敗」，
要讓使用者知道哪裡需要修。

<label asp-for="Input.Email"></label> <input asp-for="Input.Email" class="form-control"> <span asp-validation-for="Input.Email" class="text-danger"></span>

Email 格式不正確

錯誤靠近欄位；修正後可以再次送出。

錯誤訊息本身也是介面設計15

PAIR TEST

測試者不改程式，
只交付一份可重現的回報。

1

輸入

清楚說明用了哪一組假資料。

2

操作

說明按了什麼、在哪個畫面發生。

3

結果

比較預期與實際，不只說「壞掉」。

回報句型：「我輸入＿＿，按下送出後，預期＿＿，實際看到＿＿；請先檢查＿＿。」
使用課堂假資料；不要輸入真實 Email、電話、密碼、連線字串或 API key。
好回報能讓下一個修改更小、更準22
